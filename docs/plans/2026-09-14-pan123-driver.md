## 0. 一句话方案

新增 L1 驱动 crate `crates/drivers/ck-pan123`（feature / backend 键 / 配置前缀 **`pan123`**，crate 名不可数字开头），照 ck-baidu 四件套结构实现 `StorageDriver` + `CloudTransport` 双面；**主参考路线 = web API**（pan123-rs 的 Rust SDK 2862 行 MIT 全套 + PCFS 驱动形态对照），官方开放平台为备选路线（直链空间/VIP 门槛待 spike）；OSS/S3 presigned PUT 直传零自研签名（服务端下发 presigned URL，纯 HTTP PUT）；组合根接入第 6 个 feature；L2 以上零改动。

## 0.1 三参照的分工

| 参照 | 角色 | 取什么 |

| **alist `123_open`** | 备选路线（开放平台）参照 | client_id/secret 流、直链空间/VIP 门槛、QPS 形态（中文文档全白盒） |

## 1. 路线裁决（123-0 的核心产出）

### 1.1 路线 B：web API（**推荐主路线**——pan123-rs 实证 Rust 可行）

- **域名**：`api.123278.com`（**动态域名发现** `/api/dydomain` 防封轮换——客户端启动时解析，失败回退默认）+ `login.123pan.com`。
- **认证**：QR 三端点（`/api/user/qr-code/{generate,result,wx_code}`，123 App/微信扫码）或密码 `sign_in` → token；请求**双头**：`Authorization: Bearer {token}` + `Cookie: sso-token={token}`；`Origin/Referer: https://yun.123pan.cn` 必带。
- **签名**：pan123-rs 实测形态 = `dynamic_params()`（**随机 i32 key** + `timestamp-rand-rand` 值）——**无** PCFS 的 CRC32 替换表计算。两实现并存说明服务端对 key 的校验已放松；我们按 pan123-rs 形态起步，PCFS sign.go 作为回退实现（若 spike 实测拒签）。
- **上传**：`upload_request`（MD5 etag + type 0/1 + duplicate 模式）→ 服务端下发 `slice_size`（默认 16MiB）→ 逐分片 `s3_upload_object/auth` 换 **presigned URL** → `PUT` 直传 OSS → `upload_complete/v2`。**无 OSS 签名自研**（presigned 是服务端签的）。
- **下载**：`/b/api/v2/file/{download_info,batch_download_info}` → URL；**CDN 尊重 Range**（pan123-rs 续传实证：`bytes=N-` → 206/Content-Range 解析）；**`/b/api/file/download/traffic/check` 每日流量限额**（123 非会员限制——README 明示不破解、会员 9 元/月解除）。
- **文件操作**：`list/new`、`info`、`mod_pid`（移动）、`rename`、`trash`（**`event: "intoRecycle"` 删除进回收站**）、copy async（任务轮询）。
- **风险**：web 私有接口（猫鼠风险中等——作者自觉「支持官方、不破解限制」的合规姿态 + 动态域名设计说明被针对过）；**每日下载流量限额是产品级约束**（负责人若为非会员账户，挂载卷的下载量会触顶）。

### 1.2 路线 A：官方开放平台（备选）

open.123pan.cn：client_id/client_secret → access/refresh token；**下载/预览需「直链空间」**（目标文件夹手动开启 + 可能需 VIP），根目录无直链；上传支持秒传/分片。免审秒发凭证（2026 社区确认），但**直链门槛对「挂载卷 + 流式播放」这个核心场景是硬伤**——若负责人无 VIP 或不愿开直链空间，路线 A 的下载面残缺。

### 1.3 裁决规则（**已被负责人 2026-09-14 直裁关闭——D1 = web API，K64**）

原设计为「123-0 双腿并测后三选一」；负责人已直接拍板走 **路线 B（web API）**。路线 A（开放平台）降为纯文字参照（不再 spike）；123-0 的职责随之收窄为 **web API 的验证与采样**（登录/动态域名/Range/流量限额数字/upload 全链/分片状态保留/密文空 etag）。

## 3. 端点 → 契约映射（路线 B；StorageDriver 九方法）

| 方法 | 端点/机制 | 备注 |
|---|---|---|
| `list` | `/b/api/file/list/new`（分页参数 → `Page`/`Listing::next`） | 字典序稳定排序驱动内自理 |
| `stat` | `/b/api/file/info` + list 兜底 | EntryId 句柄 = file_id（i64） |
| `mkdir` | `upload_request`（type 1，目录创建即上传请求形态）+ 隐式父目录逐级 | 已存在 → 5060 处理转 `Exists` |
| `delete` | `/b/api/file/trash`（`event: "intoRecycle"`） | **天然回收站语义**——与 115 D2 拍板同形态，直接沿用 |
| `rename` | `/b/api/file/rename`（文件）；目录确认（spike 验证 rename 对目录的可用性，不可用则 mod_pid 同目录移动） | 预检目标存在 → Exists |
| `reader(range)` | `download_info` → CDN GET + `Range` | **Range 实证**（206/Content-Range）；download_info 结果缓存（TTL spike 定，参照 baidu dlink 60min 先例）；流量限额预检 `traffic/check`（超额 → `RateLimited`/明确错误而非 403 迷雾） |
| `writer(stager)` | `upload_request`（MD5 etag + duplicate）→ 逐分片 presign → PUT → `complete/v2` | commit-on-close 天然契合（complete 前 CDN 不可见）；**流式约束：MD5 前置**——队列暂存件预计算（明文卷），密文卷 etag 同理可算（永不命中秒传但格式必填） |
| `quota` | `/b/api/restful/goapi/v1/user/report/info` | 空间字段 spike 确认；**每日下载流量余量**可一并透出（web 面加成项，v1 可选） |
| 秒传（可选 trait） | upload_request 响应判 `Reuse`/存在 | `RapidUpload` + WriteHint（MD5） |
| `resume` | 分片粒度：presigned PUT 幂等重试 + 重传同路径重走 upload_request 取回 upload_id/slice 进度（**spike 验证服务端状态保留**） | 断言⑦驱动层可观测验证后才点亮 |

**错误映射表（R2）**：`code 5060`（已存在）、流量超额（`is_traffic_exceeded`）、token 失效（401 形态 → `Unauthorized{recoverable:true}` 重登/刷新一次）、presign 失败、CDN 4xx——spike 采样真机码后成表，mock 回放钉死（照 errno_mapping.rs 先例）。

## 5. 硬纪律（两仓库实战坑 + 本轮新发现）

1. **blocking → async 全量转换**：pan123-sdk 是 `reqwest::blocking`（+内部线程池并发分片）——移植进我们的 tokio 栈时改为 async + `tokio::spawn` 并发分片（或先串行起步，并行留优化）。**这是移植工作量主项**。
2. **动态域名发现**：启动时 `/api/dydomain` 解析实际 API 域，失败回退 `api.123278.com`；不硬编码单一域名（防封轮换设计）。
3. **双认证头**：`Authorization: Bearer` + `Cookie: sso-token=` 同发（pan123-rs 形态）；`Origin/Referer: yun.123pan.cn` 必带。
4. **5060 已存在码**：upload_request/mkdir 命中时按 duplicate 模式决定重试参数——我们的覆盖语义（writer 契约）用 `duplicate` 重传模式对齐（百度 rtype=3 覆盖语义同源课题）。
5. **MD5 前置 vs 流式**：etag 必填——队列暂存件预计算（我们本就暂存）；spike 确认密文卷空 etag 是否被拒（拒则照常算，代价一遍哈希 IO）。
6. **大分片超时自适应**：PUT 超时 = `max(300s, chunk_mb × 2s)`（pan123-rs 实测值，照抄）。
7. **流量限额前置检查**：下载前 `traffic/check`，超额给明确 `RateLimited` 错误（人话指引会员/次日），不撞 403 迷雾。
8. **上传后 size 校验 + 分片幂等重试**（指数退避 + jitter——其 transfer.rs 形态）。
9. **IPv4 dial**：PCFS 同款（123 同样被观测到 v6 不稳；pan123-rs 未显式处理——我们照 baidu 形态加）。

- 认证双头：`AUTHORIZATION: Bearer` + `COOKIE: sso-token=`（client.rs:1424-1427）；`Origin/Referer: yun.123pan.cn`、UA、`login_uuid`（md5(uuid)）。
- 上传细节：MD5 etag、`slice_size` 服务端下发（默认 16MiB）、分片队列多线程、presigned PUT、`duplicate` 模式与 **5060 已存在码**二次请求、大分片超时 `max(300s, mb×2s)`、目录创建也走 upload_request（type 1）。
- 下载细节：Range `bytes=existing-` 续传、206 判定、Content-Range 解析总量、resume meta 本地持久化。
- 限流：令牌桶（requests_per_second 可配）。
- **签名差异实证**：`dynamic_params()`（client.rs:1403-1413）= 随机 i32 key + `{unix_ts}-{rand}-{rand}` 值——值格式与 PCFS signPath 输出一致但 **key 无 CRC32 计算**（PCFS sign.go 用替换表+CRC32 得 key）。两实现并存 → 服务端 key 校验放松。
